# Signal GEO 四岗位团队启动计划

状态：2026-10-21 本轮团队建制已独立验收通过；产品已读取验收报告和证据，完成汇总。仅限建制，不代表新增功能或生产上线通过。

## 目标与范围

本轮只建立四岗位协作与共享上下文，验证交付和独立验收链路，不新增产品功能，不修改业务代码，不部署。当前应用是浏览器前端与 Python 本机服务，多人账号和生产权限尚未完成。

本岗位是当前任务内由主协调者创建的真实产品子 agent，负责规划和领导协调；不是已创建的桌面常驻聊天窗口。仓库中的 current_session 保持 unbound，不承诺后台守护、自动共享全部聊天或跨账号同步。

## 职责与文件归属

| 岗位 | 负责事项 | 本轮可写范围 |
|---|---|---|
| 产品 | 定义目标、交付要求与验收门槛，核对两侧交付，发起验收，汇总和返修路由 | 自己的岗位目录；必要时维护当前工作 |
| 前端 | 只读接手 dist、前端测试和页面说明，整理入口、已有检查方法及风险 | 自己的岗位目录 |
| 后端 | 只读接手 server.py、tools、Python 测试和运行说明，整理接口、数据流及风险 | 自己的岗位目录 |
| 验收 | 两侧交付后独立核查本轮建制范围、文件和证据，反馈问题；不代写业务代码 | 自己的岗位目录 |

Git 分支、提交、推送由主协调者串行管理；本轮子 agent 不执行这些操作。后续业务任务中 dist 归前端，server.py 与 tools 归后端；公共接口、测试数据和跨岗位文件先由产品指定唯一修改者。

## 前后端交付要求

两侧分别提交自己的接手说明，并在各自 worklog 索引。交付必须包含：

1. 已读取的事实源与所处业务入口，现有实现和职责边界。
2. changed_files/output_paths：仅列真实修改与可读取的证据路径；业务代码无需修改须明确说明原因。
3. verification：实际执行的只读检查或适用测试命令、结果；未运行的测试写明未测与原因，不能把静态阅读称为运行通过。
4. risks：现有风险、受阻项、未完成事项，区分“接手发现”与“本轮造成”。
5. next_action 与 acceptance_needed：后续建议、交给其他岗位的事项，以及验收应核查的内容。

前端应覆盖页面入口、主要报告信息结构、页面验证入口；后端应覆盖服务入口、关键接口与数据/分析链路、运行和测试入口。无需为了完成接手而启动服务、制造数据或修改业务逻辑。

## 验收门槛

产品确认前后端两份交付均可读取且字段齐全后，才把两份路径、产品计划与检查范围交给验收。此前验收只能准备清单。

验收应独立核查：

- 四岗位职责、可写范围、launch、worklog 与共享上下文入口可读取且一致。
- 前后端说明准确对应现有文件，检查命令与结果有证据；缺失、未测和受阻分别标记。
- 本轮无新增业务功能，无越界修改、Git 并行操作或发布声明；用户原有变更须与本轮修改区分。
- 共享靠文件和真实消息完成，桌面会话未绑定；真实子 agent 与桌面常驻会话没有混淆。
- 不把未知当零、不把提及当推荐、不把普通链接当 AI 原生引用，不编造数据或线上验证。

通过条件是本轮建制交付与上述边界全部满足。任何业务测试未运行，只能描述为未测，不据此推断功能、线上部署或生产权限已通过。验收给出结论、证据路径，以及问题的复现步骤、预期/实际、严重程度、责任岗位。

## 后续任务路由

1. 前端与后端 → 产品：两侧接手说明就绪；无需业务修改须显式回报。
2. 产品 → 验收：核对完整性后发起本轮建制独立验收，附两侧输出路径。
3. 验收 → 产品：通过、未通过或受阻，附独立验证证据。
4. 产品 → 对应岗位：缺少交付退回补齐；页面问题给前端，接口/数据问题给后端，边界或契约冲突由产品裁定文件归属；修复后再交验收复核。
5. 产品 → 主协调者/用户：汇总本轮结果与剩余限制。新的业务需求需另行定义目标、验收条件、互斥文件范围与依赖后再启动开发。
