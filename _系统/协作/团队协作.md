# Signal GEO 团队协作

## 一个项目，四个岗位

| 岗位 | 职责 | 主要可写范围 | 交付对象 |
|---|---|---|---|
| product · 产品 Agent | 规划、任务拆解、优先级、接口协调、验收标准、交付汇总 | 当前项目、当前工作、产品岗位目录 | 前端、后端、验收、用户 |
| frontend · 前端 Agent | 页面设计、交互、响应式、可访问性、证据展开 | dist、前端测试、前端岗位目录 | 产品、验收 |
| backend · 后端 Agent | 接口、数据、分析逻辑、运行服务 | server.py、tools、Python 测试、后端岗位目录 | 产品、验收 |
| acceptance · 验收 Agent | 读前后端交付，独立检查并给反馈；不替开发岗位改业务逻辑 | 验收岗位目录 | 产品及对应开发岗位 |

## 共享上下文

- 项目事实：`_系统/上下文/当前项目.md`。
- 当前任务及进度：`_系统/任务/当前工作.md`，由产品维护。
- 岗位索引：`_系统/协作/agent-lanes.md`。
- 共享输出和请求：`_系统/协作/shared.md`。
- 各自交付及过程记录：`_系统/协作/lanes/<岗位>/worklog.md` 与 workspace。

每次开始工作先重读事实源和最新交付，不假定聊天历史相同。其他机器需同步相应 Git 分支才能读取新增上下文；不包含密钥和客户原始私有资料。

## 一轮任务的执行顺序

1. 产品写明目标、验收条件、文件归属和前后端接口约定，创建明确任务。
2. 前后端在各自文件范围内执行，可以并行；跨边界修改必须先协调。需要共改测试数据或入口文件时，产品指定唯一修改者。
3. 两边分别在自己的 worklog 回报 changed_files、verification、risks、next_action、acceptance_needed。无需修改的一侧必须给出明确理由，不能默默跳过。
4. 产品核实两个交付都已就绪，再通知验收。验收在此之前可准备检查清单，但不提前宣布通过。
5. 验收独立执行适用测试和界面检查，反馈可复现步骤、预期/实际行为、严重程度和责任岗位。
6. 有阻断问题：回到对应开发岗位返修，再复验；通过后产品汇总。发布状态单独说明。

## 会话与自动化边界

仓库中的角色配置和岗位文件可复用，不等于四个桌面端常驻聊天窗口。当前任务可由主协调会话创建四个真实子 agent，并在收到回报后继续调度；任务结束后不宣称存在持续轮询、定时执行或后台守护。

如果宿主没有创建独立桌面会话的工具，StarWork 岗位的桌面会话绑定保留 unbound，提供各岗位的 `launch.md`。在支持的 Codex 客户端信任并打开本项目后，可以使用四个自定义角色，或把 launch.md 粘贴到新建的同项目会话。

## 本轮授权：网址自动诊断与逐题模型下钻

用户已授权在 url-diagnosis-flow 分支打通输入网址后的诊断、已有模型自动出题采样和逐题 box/dialog 工作流。产品契约见 `_系统/协作/lanes/product/workspace/网址诊断工作流契约.md`。

本轮前端可写 dist 与 tests/*cjs，后端可写 tools 与 Python 测试；公共 fixtures、README、QUICKSTART 和浏览器 E2E 由主协调者唯一修改。产品维护产品/共享上下文文档，不改业务；验收等两侧交付后独立检查真实 HTTP 与浏览器页面。无模型凭据仍可执行真实网页检查；fixture 集成不得冒充真实多模型调用。Git 仍由主协调者串行处理。
